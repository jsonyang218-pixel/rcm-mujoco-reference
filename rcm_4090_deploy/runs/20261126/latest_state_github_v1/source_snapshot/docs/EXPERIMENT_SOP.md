# 实验 SOP

适用于数据采集、训练、离线与闭环评估、消融和比较。聊天里的一句话、已有实验卡、
多阶段任务规划都默认按本 SOP 处理，无需额外说“按 SOP 执行”。

## 先判断授权范围

| 请求 | 行为 |
|---|---|
| 只要规划 | 整理实验卡、门禁和预算；可以只读核对现有资产，不启动实验。 |
| 执行已有规划 | 直接把规划当卡，保留已给参数、先后顺序、分支和停止条件；不要求重填。预检通过后自动执行已授权阶段。 |
| 新一轮训练并测试 | 预检通过后在新的 GNOME Terminal 启动一次。训练、验证和门禁通过后自动闭环。启动后助手不等待、不轮询、不主动发阶段进度；用户再次发消息时才查一次。终端打不开就报告，不后台回退。 |

只在缺失项或冲突会阻碍安全或可比执行时询问。不要默默替换训练数据、初始化权重、
评估协议、设备或预算；门禁失败后停掉依赖它的阶段，不改参数或自行重跑。

## 实验卡与预检

一张卡应写清：假设与主要改动；不变的对照条件；训练/验证数据及隔离方式；
初始化与待测权重、模型入口和基线版本；评估目标档位、种子和协议；训练轮数、闭环最大步数、
分片数、各阶段时间上限；门禁、依赖和分支；结果存放路径。无关项写明不适用。
训练前确认模型和 checkpoint 架构匹配、数据和场景资产存在、基线可比较、输出是新路径。
CUDA 工作使用部署 `.venv`、物理 GPU 0（RTX 4090）、`MUJOCO_GL=egl`，保持训练 AMP 默认值。

标准训练/验证/闭环复用 [模型流水线](MODEL_PIPELINE.md)。
[固定 10 目标示例卡](../configs/experiment_card_screen10_example.json) 使用已有权重，
不训练；门禁要求最终误差均值低于基线。正式运行应选未占用的版本化目录。
在 `rcm_4090_deploy/` 执行：

```bash
source .venv/bin/activate
python -B -m scripts.tools.experiment_workflow preflight --card configs/experiment_card_screen10_example.json
python -B -m scripts.tools.experiment_workflow launch --card /path/to/card.json
python -B -m scripts.tools.experiment_workflow status --output-dir outputs/experiment_version
```

- `preflight` 仅读取卡和资产，输出检查结果与实际命令，不创建实验目录、不启训练或闭环。`launch` 会自行预检，单独运行 `preflight` 并非启动前的必需命令。
- `launch` 默认新开 GNOME Terminal，不使用 `--wait`，只返回启动是否被接受。显式 `--terminal current` 可用于获准在当前终端执行的规划或测试，不作为 GNOME 失败的回退。
- `status` 只读一次状态，不监听、恢复或触发实验。`partial_summary.json` 不是最终结果；如果评估完整但指标门禁失败，会保留最终摘要，并单独标记门禁失败。

### 多阶段卡

`pipeline` 阶段省略 `checkpoint` 时按 `config` 训练、验证，再用本次最佳权重闭环。
可用 `max_val_loss` 对最佳验证 loss 设上限，失败则不启动闭环。用 `checkpoint_from`
引用前置训练阶段权重时，该阶段只做评估。`module` 阶段可调用已有的 Python 模块，
用 `module` 与 `args` 保留原有参数，并显式列出外部 `assets`；脚本必须支持 `--output-dir`
且不得自行派生未授权的实验。各阶段输出到卡目录下的同名子目录。

阶段依卡的顺序处理，默认依赖紧邻的上一阶段；`requires` 可显式列出若干前置阶段，
`[]` 表示独立。`gates` 从本阶段最终 JSON 用点分键读取有限数值，支持 `<`、`<=`、`==`、
`>=`、`>`。`when` 同样读取最终指标，但需增加 `stage` 指向一个依赖：条件不满足是分支未选，
不是实验失败。需要在筛选后确认时，只有在卡中已授权 `dev20` 且依赖、门禁通过，才运行它。
训练/评估、预检或门禁失败不重试；超时和可捕捉的中断会停止子进程并保留证据。

## 评估档位与复用

| 档位 | 用途与范围 |
|---|---|
| `smoke` 冒烟 | 1–3 个显式目标、短步数和小预算；只验证数据/权重/渲染/推理/记录链路，不作为模型改进证据。 |
| `screen10` 固定筛选 | 冻结可达 development 清单索引 `0–9`，按同目标、同种子、同协议与登记基线配对。用于筛选候选，不外推为完整成功率。 |
| `dev20` 完整确认 | 同一清单索引 `0–19`，覆盖完整 development 集；不等于独立 `final_test`，后者需另行授权。 |

默认当前严格对照是 `seed=42+episode_index`、每目标最多 1600 步、50 ms 控制周期、
0.35 µm 和连续 3 帧编码器停稳，动作采样与执行步数沿用卡内协议。
不能为过门禁改目标、种子、停止条件或筛选指标。10 与 20 的分母分别报告。

仅当已有评估完整，且权重、执行代码、场景、目标顺序、逐目标种子及协议都可核对并一致，
才允许复用，不能用训练 loss、分片汇总或较小目标集替代。已完成的 SOP 流水线写
`evaluation_receipt.json`；在评估阶段用 `reuse_from` 显式引用其目录。无凭据、目标覆盖不全
或不匹配时拒绝复用，也不自行重跑。冻结历史基线可按有据可核对的范围用于配对参照，
若缺代码/场景指纹，应注明是历史参照，不当作本轮可复用评估；不改冻结资产。

## 进度和报告

真实训练日志、逐轮验证 loss、闭环步数及分片完成数同时显示和落盘。主要阶段结束打印结果路径；
`workflow_status.json` 是卡级状态，`preflight.json` 保存实际命令与输入指纹，子阶段保留原流水线文件。
中断（Ctrl+C、捕捉到的终端关闭信号或超时）保留进度，记入 `TEST_LOG.md`。不可捕捉的强杀或断电
不保证自动登记，发现后须补记已完成范围，不得把残留状态当成功。

正式报告分开陈述：**流程完成**（完成几阶段、几分片、几目标）、**指标改善**（基线、协议、
同目标差值和是否通过卡的门禁）、**严格成功**（按阈值与停稳判定的成功数/总数）。
失败、中断、无基线和数据缺失均如实标明。所有结果只验证软件与 MuJoCo 仿真，不代表临床精度或硬件就绪。
路径遵循 [输出组织规则](OUTPUT_LAYOUT.md)，已完成、失败和中断的结果追加到 [TEST_LOG.md](../TEST_LOG.md)。
