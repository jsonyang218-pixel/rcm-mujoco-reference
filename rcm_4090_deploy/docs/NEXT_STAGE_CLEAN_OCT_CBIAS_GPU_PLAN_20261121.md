## GPU 执行原则

部署工作目录固定为 `rcm_4090_deploy/`，使用 `.venv/bin/python`。
所有 CUDA/EGL 子进程继承：

```bash
CUDA_VISIBLE_DEVICES=0
MUJOCO_GL=egl
MUJOCO_EGL_DEVICE_ID=0
MPLBACKEND=Agg
PYTHONDONTWRITEBYTECODE=1
```

启动时检查 CUDA 设备与实际 EGL 渲染设备；环境变量本身不算 GPU 渲染验证。
训练保留现有 FP16 AMP 与 GradScaler。CPU 负责文件读取、PNG 解码、日志及现有 MuJoCo/电机积分；
GPU 执行网络计算和 EGL 图像渲染。现有仿真没有因此转成 GPU 物理，不能把它记为已采用 MJX。

目标是提高每秒完成的有效帧、训练批次及目标数。GPU 利用率和显存占用作为诊断数据，
不能靠增加无效计算或仅占满显存来宣称提速。

## Stage 1：把重渲染分成独立 EGL 分片

1. 固定原计划 `<200 µm` 条件，冻结候选行号；新旧 OCT 独立保存，原始数据不覆盖。
2. 先构建共享场景资产，再启动渲染工作进程。每个进程独立持有场景和 EGL 上下文；
   按 episode 分配任务，进程内复用模型、渲染器和相机配置，减少反复加载与创建上下文。
3. 建议同一次运行起始 **4 个进程、最多 8 个**。处理正常任务时记录吞吐与资源，
   仅在显存、系统内存均有余量且总吞吐提高时增加任务并发；不启动额外训练或重复目标做压力测试。
   预留至少 6 GiB 显存和 6 GiB 系统内存；单进程初始化需求、GPU 峰值及 CPU 内存也纳入准入。
   4/8 是待验证的资源调度建议，不是已证明的最优并发数。
4. 多进程阶段限制每进程 BLAS/OpenMP/PyTorch CPU 线程数，避免线程数乘上进程数耗尽 CPU。
   图像处理供给不足时调整工作线程，记录实际配置。
5. 固定 `offsamples=0, numslices=112, numstacks=64` 和原来的严格 RGB-D 测量定义；
   不为速度降低分辨率、换渲染质量或用真值替代视觉 OCT。真值仅用于离线审计。
6. 每个分片原子落盘，再提交完成记录；检查原数据、行号、场景、渲染设置和代码指纹后才允许复用。
   不完整分片标为 partial，不能当作完成。任务失败保留证据，不自动重试。
7. 按原计划抽样 200 帧，核对新 OCT 与相应相机坐标真值；中位误差 `<0.2 µm` 是数据门禁，
   同时报告有效率、尾部误差和未完成行数。C 轴先审计，再按原条件决定是否生成修复覆盖层，单步上限仍为 `0.030 mm`。

107,343 帧若要在 40 分钟内完成，仅渲染就需要 **至少 44.73 帧/秒**的总吞吐，
还未计入审计、写盘与初始化。现有三进程闭环耗时不能证明该吞吐可达。
保留原计划 40 分钟上限时，超时应记录 partial 并跳过训练，不能假装覆盖层已完整。
不得静默减少帧数或延长预算。

## Stage 2：单训练任务集中使用 CUDA

- 沿用指定检查点与现有 State-Attention v1；不增加 symlog 分支。
- 建议继承 Task 2 的有效训练参数：batch size 16，AdamW，backbone LR `1e-6`，attention LR `1e-5`，
  weight decay `1e-4`，训练 seed `20261118`，验证 seed `20261119`，4×1,000 batches。
  这是从现有训练配置补全的建议，不应把文件中历史遗留的 `lr=1e-4` 当作当前两组实际学习率。
- 保留 AMP、梯度裁剪、pinned memory、异步 CPU→CUDA 传输；训练入口现有这几项支持。
  现有 DataLoader 为 8 workers、prefetch factor 2；避免改了配置字段却没有改实际加载器。
- 不并行训练多个副本争抢同一 GPU；训练、验证按现有顺序执行。
  增大 batch 会改变 4,000 batches 对应的样本数和更新过程，需另列实验，不能作为本轮默认提速措施。
- 模型归一化从初始化检查点继承。验证集建议沿用 `data/lerobot_rcm_val_acthist_20261117_224`，
  与训练轨迹隔离；如验证观察仍是旧 OCT，应在结果中说明，不能把验证 loss 当作新渲染闭环改进。
- 原采样器按 action-source 划分 teacher/executed 窗口，8% 对应 teacher 回放池，
  4,000×16 共 64,000 样本，其中 teacher 5,120、executed 58,880。
  `<200 µm` 清洗帧分布在两池；“8% teacher 回放”不等于“只有 8% 样本用了清洗 OCT”。
  若原计划想重新定义 clean/unclean 两池，应先明确池定义，不能直接复用旧采样器宣称满足要求。
- `dagger_repeat=1` 的意图是取消额外重复加权；该训练入口没有这个命令行参数，
  应通过唯一窗口池和原 ratio sampler 落实，不能引用继承配置中遗留的 `dagger_repeat=10` 作为实际行为。
- `--init-from` 是加载模型、创建新优化器的热启动；不是优化器、AMP、随机状态的精确断点恢复。
  遇到非有限 loss/梯度/验证值应中止、保留最后完整检查点并跳过依赖评估，不自动回退重训。

## Stage 3/4：按目标分片，增加 GPU 并发

保留两批依赖：先在 V0 上比较新 step 2,000/4,000，再对胜出权重运行 V3/V2。
各批把 `(checkpoint, variant, target_index, seed)` 作为独立任务分发，
建议同样起始 4、上限 8 个工作进程，每进程复用模型、渲染器。
每个任务使用独立场景、控制器、动作历史和按目标重置的随机状态，禁止共享有状态控制器。

保持原 I0、Flow 4、samples 1、execute 1、50 ms 控制周期以及 P2 `(32,32,32)` 单包限幅。
每个目标完成后立即原子写入结果、更新 partial summary 和带 SHA256 的复用凭据。
复用必须匹配权重、代码、场景、驱动、目标、seed 和完整协议。
终止发生在 episode 内时保留轨迹，不能仅凭最后几行输出跳过该目标。
本方案不承诺恢复到某个 MuJoCo 帧；完整进程状态和 RNG 尚未实现持久化。

本轮先采用独立进程 CUDA 推理。跨环境批量推理可作为后续优化，
但必须先解决每个目标的 Flow 随机噪声与 batch 顺序一致性，不能把“计划批量化”写成已实现。

- fast5 保持 E00/E02/E06/E08/E10，seeds 42/44/48/50/52，每目标 1,000 步。
- Stage 3 最优均值 `<45 µm` 仍是原定的条件门禁，不把它描述为已经证明的统计显著性。
- dev20 仍为索引 0–19、seeds 42–61、每目标最多 1,600 步。
- 用户于 2026-11-21 以“可以,启动”批准单目标预算修订：1,000 步 600 秒、
  1,600 步 900 秒，替代原文 180 秒；更高并发的实际耗时仍需验证。
- 原 Stage 3 两批合计 20 个 episode。并发数必须结合每目标实际耗时估计整批预算，
  不能套用上一轮“三种 variant 各串行 5 目标”的调度器并承诺 25 分钟完成。
- 原计划省略了 SOP 的固定 screen10。fast5 只能标注诊断筛选；
  正式执行前需明确接受这个范围例外，或另行补全 screen10 及其预算，不能默默增加评估。
- G10 视觉教师约 1.70 µm 是已有 fast5 的 1,600 步结果，不能直接当 dev20 配对基线。
  没有同档位同目标完整教师证据时，dev20 的教师超额误差写“不可配对”，不外推或自行加跑。
